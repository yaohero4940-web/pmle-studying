你在一家大型在线零售商工作。你正在将一个需求预测模型投入生产，用于预测未来销量以支撑库存管理。

你需要每 30 天用新数据重新训练一次模型。库存规划团队需要每日的批量预测结果来生成补货订单。

你需要设计一个既能生成每日预测、又能把资源成本降到最低的方案。你应该实现哪种流水线架构？

选项

A. 在 Agent Platform Pipelines 中调度一个每天生成批量预测的流水线。把训练作为一个条件步骤，仅在周期第 30 天时执行。

B. 在 Agent Platform Pipelines 中实现两条流水线：一条每 30 天运行一次的持续训练（continuous training）流水线，以及一条每天运行一次批量预测作业的批量预测流水线。

C. 在 Agent Platform Pipelines 中实现一条每 30 天运行一次的流水线，用于训练并在 Agent Platform endpoint 上更新带版本的模型。配置一个 Cloud Run function，把每日批量数据集发送到该 endpoint 做预测。

D. 在 Agent Platform Pipelines 中实现一条流水线，按顺序执行数据准备、模型训练和批量预测三个步骤，并将该流水线调度为每天运行一次。

正确答案与详细讲解默认折叠 · 点击展开
正确答案BA ✗B ✓C ✗D ✗
核心考点：训练与批量预测按不同频率拆分

【这道题在说什么】

你在大型在线零售商工作，要把一个需求预测模型投产：它用来预测未来销量、支撑库存管理。业务上有两个节奏不同的需求——模型要每 30 天用新数据重训一次，而库存规划团队每天都要一份批量预测结果来生成补货订单。要求设计一套既满足「每天出预测」、又把资源成本压到最低的流水线架构。核心矛盾是——训练和预测的频率不一样（30 天 vs 每天），怎么组织才不浪费。

【先搞懂几个概念】

  • 批量预测（batch prediction）：一次性对一大批数据打分，是异步作业，按实际处理的数据量计费。适合大规模离线场景，比如每天给所有商品生成一次预测。
  • 在线预测（online prediction）：模型常驻服务，收到单条请求就即时返回，需要常驻副本，成本高。适合实时交互式请求。
  • 持续训练（continuous training）：定期用新数据重新训练模型的流水线，是 MLOps 的基础环节之一。
  • 流水线调度频率（schedule frequency）：不同任务的执行频率可以不同。频率不同的任务最好各自调度，避免互相拖累。
  • 条件步骤（conditional step）：在流水线里加一个 if 判断，满足条件才执行某一步。
  • Cloud Run function：事件驱动的小代码执行单元，常用来做「定时触发 / 转发」这类胶水逻辑。
  • 成本来源：闲置的常驻在线服务、每天重复跑的昂贵训练步骤、以及每次启动整条流水线都要付出的调度与环境准备开销。
  • 频率匹配原则：让每个动作按它真正需要的频率执行，不多跑一次，这是最省成本的架构思路。把「低频的重活」和「高频的轻活」绑定在一起，必然要为其中一方多付钱。

【题目给的约束条件（解题钥匙）】

  • "retrain ... every 30 days"（每 30 天重训一次）→ 训练是低频、开销大的动作。
  • "daily batch predictions"（每天一次批量预测）→ 预测是高频、且明确是「批量」，不是在线请求。
  • "minimizing resource costs"（把资源成本降到最低）→ 不许多花钱，排除每天重训这种浪费。
  • 两个动作频率明显不同（30 天 vs 每天）→ 暗示应该拆成两条独立调度的流水线。

【正确答案为什么是 B】

选项 B：在 Agent Platform Pipelines 里实现两条流水线——一条每 30 天运行的持续训练流水线，一条每天运行的批量预测流水线。它的工作机理是：训练流水线低频运行、开销大；预测流水线高频运行、开销小（批量预测按量计费）；两者各按自己真正的频率执行，互不拖累。既不会出现「每天为判断是否要训练而启动整条流水线」的空转开销，也不会有常驻在线服务的持续成本，职责还更清晰。这是成本最优、结构最干净的方案。

【其他选项为什么不行】

  • 选项 A 一条流水线 + 条件步骤：条件步骤是真实存在的能力（例如判断是否是周期第 30 天）。但为了做这个判断，整条流水线每天都要被启动一次，调度、环境准备、编排这些固定开销天天都在发生，不如干脆拆成两条省。它是「能用但不经济」。
  • 选项 C 训练流水线 + Cloud Run function 打 endpoint：这条方案里训练那条是合理的，问题出在预测：用 Cloud Run function 把每日批量数据打到「在线 endpoint」，等于用昂贵的常驻在线服务去做离线批量打分，成本明显更高；而且在线接口通常还有请求大小和 QPS 限制，不适合大批量数据。用错了预测方式。
  • 选项 D 每天跑「数据准备 + 训练 + 预测」：把重训频率从每 30 天硬提到每天，训练资源被浪费大约 29 倍，直接违背「成本最低」。这是本题最明显的成本陷阱。

【这个考点还会怎么考】

  • 变体一：「训练与预测频率不同」→ 拆成两条独立流水线，各按自身频率调度。
  • 变体二：「离线大批量打分」→ 用 batch prediction；「实时单条请求」→ 用 online prediction / endpoint。
  • 变体三：出现「每天重训，却其实只需每月重训」的选项 → 就是成本陷阱。
  • 变体四：「要求最低延迟的实时预测」→ 才需要考虑 endpoint 常驻服务。
  • 变体五：「要进一步压成本」→ 减少常驻服务、尽量用按量计费的批处理。
  • 变体六：把「每天批量预测」改成「每几分钟出一次小批量预测」→ 仍是 batch prediction，但要注意调度频率与单批数据量的平衡，避免过于频繁导致固定开销占比过高。

【一句话记住】

> 训练与预测频率不同 → 拆成两条流水线；离线大批量打分用 batch prediction，别拿常驻 endpoint 干这活。

你在一家金融公司工作，该公司拥有一个包含一万亿 token 的大型自定义数据集。

该数据集包含金融新闻、报告及其他相关数据，并已采购了类似 Common Crawl 的大型公开数据集。

你需要使用开源的开放语言模型 (OLMo) 框架从零开始训练一个自定义 LLM，并希望最大化吞吐量。

你应该怎么做？

A. 将数据集存放在 Filestore 中，并创建一个由 a4-highgpu-8g 机型（使用 B200 GPU）组成的 GKE 集群。把 PyTorch 工作流封装成一个调度到该集群上的 Google Kubernetes Engine (GKE) job。

B. 购买 B200 GPU 的预留（reservation）。使用 Managed Lustre（托管 Lustre 并行文件系统）存放数据，并使用 Cluster Toolkit 创建一个由 a4-highgpu-8g 机型（使用 B200 GPU）组成的 Slurm 集群。在该集群上调度一个 PyTorch 训练作业。

C. 将数据集存放在 Filestore 中并挂载为 NFS。在 B200 GPU 上运行一个基于 PyTorch 作业的 Agent Platform 自定义训练作业。

D. 将数据集存放在 Cloud Storage 中，并使用带 a4-highgpu-8g 机型（使用 B200 GPU）的抢占式虚拟机（preemptible VMs）创建一个 GKE 集群，在该集群上调度 PyTorch 训练作业。

正确答案与详细讲解默认折叠 · 点击展开
正确答案BA ✗B ✓C ✗D ✗
核心考点：大规模从头预训练的算力与存储选型

【这道题在说什么】

你在金融公司，手里有一个一万亿 token 的自定义数据集（金融新闻、报告，外加类似 Common Crawl 的大型公开语料）。你要用开源的 OLMo 框架从零开始训练一个自定义 LLM，目标是最大化吞吐量。换句话说，这是超大规模预训练任务，问题不在算法，而在「算力怎么给、数据怎么存、作业怎么调度」这三件事怎么配才最快。

【先搞懂几个概念】

  • 从零预训练（pretraining from scratch）：不基于别人训好的模型，直接用海量语料从头训练一个大语言模型。它是整个 LLM 生命周期里最贵、最耗算力的阶段。
  • OLMo（open language model）：一个开源的开放语言模型框架，提供从数据、训练到评估的完整工具链。
  • 吞吐量（throughput）：单位时间能处理多少 token。越大越好，是本题的优化目标。
  • HPC（高性能计算）场景：超大规模训练需要的是「大规模、低延迟、高带宽的加速器集群」加上「拓扑感知的作业调度」，这更像传统超算，而不是普通云服务。
  • Cluster Toolkit：Google 提供的工具，用来快速搭建 HPC 集群（尤其 Slurm 集群），把机器、网络、存储按最佳实践配好。
  • Slurm：经典的高性能计算作业调度器，擅长管理大规模批量训练作业、做资源分配与排队。
  • 预留（reservation）：提前锁定一批 GPU 资源，保证大规模训练时算力一定拿得到，不会被别的任务抢走。
  • Managed Lustre：托管的 Lustre 并行文件系统，专为高吞吐、大规模并发读设计。当成千上万块 GPU 同时要读数据时，它能扛住 I/O 压力。
  • Filestore / NFS：通用的网络文件系统，读写方便但吞吐有限，在这种极端规模下很容易成为瓶颈。
  • Cloud Storage（GCS）：对象存储，适合存海量数据，但在「海量小文件高频并发读」这种训练场景下吞吐不如并行文件系统。
  • 抢占式 VM（preemptible）：价格便宜但随时可能被回收。适合可中断的短任务，不适合动辄数周的大模型预训练。

【题目给的约束条件（解题钥匙）】

  • "one trillion tokens"（一万亿 token）→ 数据量极大，存储必须能承受海量并发读取，这是选存储的关键。
  • "train a custom LLM from scratch"（从零训练）→ 长周期、算力密集，需要稳定的大规模算力供给和可靠的作业调度。
  • "maximize throughput"（最大化吞吐）→ 要 HPC 级算力、高吞吐 I/O、合适的集群调度三件套。
  • 使用 OLMo + PyTorch → 是典型的大规模训练技术栈，需要在集群上调度训练作业。

【正确答案为什么是 B】

选项 B：购买 B200 GPU 的预留，用 Managed Lustre 存放数据，并用 Cluster Toolkit 创建由 a4-highgpu-8g 机型（B200 GPU）组成的 Slurm 集群，在其上调度 PyTorch 训练作业。它的工作机理是：预留锁定了大规模 GPU 供给，保证算力不会中途断供；Managed Lustre 提供高吞吐的并行 I/O，让上万 GPU 同时读数据也不成瓶颈；Slurm 集群（由 Cluster Toolkit 按最佳实践搭建）做大规模、拓扑感知的作业调度。算力、存储、调度三件套齐备，正是 Google 官方给出的最大化吞吐组合。

【其他选项为什么不行】

  • 选项 A GKE + Filestore：用 GKE job 跑训练是真实可行的，问题出在存储——万亿 token 数据集放在 Filestore（通用 NFS）上会成为 I/O 瓶颈，GPU 常常在等数据，整体吞吐被拉低。
  • 选项 C Filestore 挂 NFS + 自定义训练作业：同样是 Filestore 的吞吐瓶颈；而且超大规模多节点场景下，托管自定义训练作业的调度能力弱于专门的 Slurm 集群。
  • 选项 D 抢占式 VM + Cloud Storage：抢占式 VM 随时可能被回收，对动辄数周、需要频繁 checkpoint 的大模型预训练风险极高，一次回收可能浪费大量进度；Cloud Storage 对象存储在海量小文件并发读下的吞吐也不如并行文件系统。

【这个考点还会怎么考】

  • 变体一：超大规模预训练 → 预留 GPU + Slurm / Cluster Toolkit + Managed Lustre。
  • 变体二：看到 Filestore（通用 NFS）或抢占式 VM 出现在长周期大模型训练里 → 基本就是错误选项。
  • 变体三：「短期、可中断的小规模训练」→ 抢占式 VM 反而能省钱。
  • 变体四：「要托管、少运维、规模不大」→ 用 Vertex AI 自定义训练更合适。
  • 变体五：「训练时 I/O 是瓶颈」→ 换并行文件系统（Lustre），而不是继续加算力。

【一句话记住】

> 超大规模预训练 = 预留 GPU + Slurm / Cluster Toolkit + Managed Lustre；Filestore 和抢占式 VM 在长周期大模型训练里是坑。

核心考点：高频重复查询用显式上下文缓存降本

【这道题在说什么】

你在做一个基于 Gemini 的入职引导聊天机器人，它的知识来源就是 Cloud Storage 里的五份 PDF 入职文档。这些文档会按需每周或每月更新一次。你预期这个应用会收到「大量且高度重复」的用户查询，都围绕这同一批文档。现在要选一个既合适又省钱的方式来管理上下文，同时保证聊天机器人掌握的是最新信息。核心是两个词：重复（适合缓存）和更新（需要刷新）。

【先搞懂几个概念】

  • 上下文（context）：每次调用大模型时，除了用户问题，你还得把相关的背景资料（这里是五份 PDF 的内容）一起送进去。上下文越长，成本和首 token 延迟越高。
  • 上下文缓存（context caching）：把反复使用的前置内容（长文档、系统指令）缓存起来，后续请求直接引用缓存，只需付缓存读取的费用，从而显著降低成本和首个 token 的延迟。它专门解决「同一大段内容被反复使用」的问题。
  • 显式缓存（explicit cache）：由你主动创建、并显式引用；命中是确定的，存活时间（TTL）也由你控制。适合「我知道哪些内容会被反复用」的场景。
  • 隐式缓存（implicit cache）：由平台自动判断是否复用，你不需要管理；但不保证命中，省钱效果不稳定。
  • TTL（time-to-live，存活时间）：缓存的有效时长，到期就失效、需要重建。
  • RAG（检索增强生成）：按需检索相关资料塞进上下文，适合知识频繁更新、内容很大的场景。它的代价是每次都要做检索、拼上下文，某些情况下不如直接把固定内容缓存起来划算。
  • 微调（fine-tuning）：把行为 / 风格刻进模型权重，不适合用来承载「会变动的知识」；知识一变，权重里的内容不会自动更新。
  • 高频重复查询：同一份上下文被反复用到，这正是缓存发挥最大价值的前提。反过来说，如果每次查询用的资料都不同，缓存就没意义。
  • 缓存与 RAG 的区别：两者都涉及「把资料送给模型」，但缓存是把固定内容「存起来反复引用」，RAG 是「每次按需检索」。本题的资料是固定的五份文档、查询又高度重复，所以缓存更合适。

【题目给的约束条件（解题钥匙）】

  • "five PDF ... high-volume, repeated user queries"（五份 PDF，大量重复查询）→ 固定上下文 + 高频重复，是上下文缓存的理想场景。
  • "documents are updated weekly or monthly as needed"（文档按需每周或每月更新）→ 更新节奏不固定，缓存需要能随源变化而刷新。
  • "most appropriate and cost-effective solution"（最合适且最具成本效益）→ 既要省钱，又要方法对路。
  • "ensuring that the chatbot has up-to-date information"（确保信息最新）→ 缓存不能长期陈旧，必须在源文件变化时同步。

【其他选项为什么不行】

  • 选项 A 用 PDF 文本微调 Gemini：微调是真实能力，但用它来灌知识有两个硬伤：一是昂贵；二是无法做到「文档一更新就同步」——知识被固化进权重后，要更新就得重新微调。微调是教「行为 / 风格」的，不是用来承载频繁变动的知识。

  • 选项 D 显式缓存 + 固定 7 天 TTL：显式缓存方向对，但「固定 7 天」与文档「按需」更新的节奏对不上——如果文档在 7 天内变了，缓存还是旧的，信息就过期了；如果文档没变，到期又白白重建一次。两头不讨好。

  • 变体二：「知识会频繁更新」→ 用 RAG，或在源变更时重建缓存。

【这道题在说什么】

你在银行的反欺诈部门，每天要处理数百万笔信用卡交易，要做的是实时欺诈检测模型。难点在于原始数据不够丰富，需要现造「与时间相关的聚合特征」，比如「过去一个月的平均交易金额」「距离上一笔交易过去了多久」。题目问的是：为了同时支持模型训练和模型服务（在线实时预测），这些数据该怎么处理？核心矛盾是既要实时，又要保证训练和线上用同一套特征口径。

【先搞懂几个概念】

  • 特征工程（feature engineering）：从原始数据里加工出对模型有用的输入变量。原始交易只有金额、时间、商户等字段，信息量不够，所以要加工成「近一个月均值」这类更有判别力的特征。

  • 时间窗口（windowing）：把无界的流式数据按时间切成一段一段（如滑动窗口、会话窗口），在每一段上做聚合。它是流式处理里做「滚动统计」的标准手段。
  • 实时推理 / 在线预测（real-time / online prediction）：交易到达时立刻给出预测，要求低延迟；与之相对的是 批量预测（batch prediction），即周期性对一批数据打分。
  • 训练 / 服务一致性（training-serving skew）：训练时算特征用的逻辑，和服务时算特征用的逻辑如果不一致，模型线上表现就会莫名其妙地变差。这是本题最大的隐患。
  • 特征存储（Feature Store）：集中存放特征的服务，训练时从中取历史特征、服务时取最新特征，保证两边口径完全一致。Agent Platform Feature Store 就是 Google 的托管特征存储。

  • Pub/Sub：Google 的消息队列，负责把源源不断的交易事件实时送进处理管道。
  • BigQuery ML 的 TRANSFORM 子句 / TRANSFORM_ONLY：在 BigQuery 里用 SQL 表达式做特征变换的能力，适合离线批量建模。

【其他选项为什么不行】

  • 选项 A：BigQuery ML 的 TRANSFORM 子句是真实能力，能在 SQL 里生成新特征。但它是批处理式的——特征只能在数据进仓后按批算出，无法在实时请求路径上即时计算「距上一笔交易多久」这种必须看当前时刻的特征，因此满足不了实时服务的需求。

【这道题在说什么】

你把一个深度学习模型部署到了带 NVIDIA GPU 的 Agent Platform endpoint 上，最初把自动扩缩配成「CPU 利用率目标 60%」。压测时你发现：流量上升后预测延迟明显变差，但副本数一直不变。监控显示 CPU 利用率始终低于 40%，而 GPU 利用率长期超过 90%。你要让这个 endpoint 能高效扩缩、扛住增长。

【先搞懂几个概念】

  • 自动扩缩（autoscaling）：根据负载自动增减副本数量，负载高就加副本、负载低就减副本。
  • 副本（replica）：一个模型服务实例。副本越多，能同时处理的请求越多。
  • 扩缩指标（scaling metric）：平台用来判断「要不要加副本」的信号，常见的有 CPU 利用率、GPU 利用率 / 占空比、请求数等。选的指标必须反映真正的瓶颈，否则扩缩永远不触发。
  • CPU 利用率：CPU 忙于计算的时间占比。当计算主要发生在 GPU 上时，CPU 往往很闲。
  • GPU duty cycle（GPU 占空比）：在采样周期内 GPU 处于计算状态的时间比例，是衡量 GPU 是否吃满的关键指标。
  • 预测延迟（prediction latency）：从发请求到拿到预测结果的时间，越高说明服务越吃力。
  • TPU：Google 自研的 AI 加速芯片，和 NVIDIA GPU 是不同硬件栈，换它通常需要模型适配。
  • min replica count（最小副本数）：常驻副本数，始终在线也始终计费；固定最小值意味着放弃弹性。
  • GPU 利用率（GPU utilization）：GPU 处于计算状态的时间占比。它长期接近 100%，说明单副本的算力已经饱和，只有「增加副本」才能继续提速——这正是本题扩容应该依据的信号。
  • 瓶颈（bottleneck）：整个链路里最先被耗尽的那一环。监控的意义就是找出它，再针对它配置扩缩；配置错了指标，扩缩就不会响应。

【其他选项为什么不行】

  • 选项 B：把目标 CPU 利用率降到 20% 看起来更「敏感」，但实测 CPU 一直低于 40%，降到 20% 并不会因为 CPU 达标而合理扩容，反而可能让副本长期维持在高位（CPU 一超标就加），成本高且仍然没对准 GPU 瓶颈。
  • 选项 C：把模型改到 TPU 机型是真实的硬件选型选项，但本题的问题是「扩缩指标选错了」，不是算力类型不对；换硬件还要适配模型，属于答非所问。

【先搞懂几个概念】

  • GPU 利用率：GPU 处于计算状态的时间比例。忽高忽低且频繁归零，说明 GPU 常常在「等活干」。
  • 输入流水线瓶颈（input pipeline bottleneck）：CPU 侧的图像解码、数据增强、组 batch 速度跟不上 GPU 的消费速度，导致 GPU 空转。
  • DataLoader：PyTorch 里负责加载与预处理数据、给模型喂 batch 的组件。
  • num_workers：DataLoader 里并行做数据加载 / 预处理的子进程数量。设大一点可以让多个子进程同时准备数据，缓解 CPU 侧供给不足。
  • pin_memory（锁页内存）：把数据先放进锁页内存，让 CPU→GPU 的拷贝可以走异步 DMA，减少等待时间。
  • batch size：一次喂给模型的样本数量。
  • DDP（DistributedDataParallel）：PyTorch 的多 GPU 分布式训练策略，用于横向扩展算力。
  • AMP（automatic mixed precision，自动混合精度）：用 FP16 等低精度加速矩阵运算，让 GPU 算得更快。
  • ResNet-50：经典的图像分类卷积网络，常用来做 CV 基准。
  • 数据吞吐（throughput）匹配：理想的训练状态下，数据供给速度应略快于 GPU 消费速度，这样 GPU 才不空转。一旦 CPU 侧成为短板，再强的 GPU 也要闲置等待。

【题目给的约束条件（解题钥匙）】

  • "one NVIDIA A100 GPU"（单卡）→ 单卡都没喂饱，说明问题不在算力不够。
  • "maximize GPU utilization to reduce training time"（拉满 GPU 利用率、缩短训练时间）→ 要对症解决「数据供给慢」。
  • "custom PyTorch container"（自定义 PyTorch 容器）→ 改动落在 PyTorch 的 DataLoader 上最直接、最小。

【正确答案为什么是 B】

【其他选项为什么不行】

  • 选项 A：增大 batch size 确实能让单次迭代的 GPU 计算更饱满，但每个 step 需要的数据量也随之增加——在 CPU 本来就喂不动的前提下，只会让等待更久，治标不治本。
  • 选项 C：换更多 GPU 并上 DDP 是「算力真不够」时的横向扩展手段；本题单卡都吃不饱，加卡只会让更多 GPU 一起空转，且完全不解决数据加载问题。
  • 选项 D：AMP 让 GPU 算得更快，反而会进一步拉大「GPU 计算快、CPU 供数据慢」的差距，GPU 等待更多，利用率可能不升反降，方向反了。

【这个考点还会怎么考】

  • 把「CPU 高 GPU 低」换成「GPU 高 CPU 低」：这时才轮到 AMP、更大 batch、更强算力。
  • 把训练框架从 PyTorch 换成 TensorFlow：对应的是 tf.data 的 prefetch / parallel map / cache 优化。
  • 强调「数据在云端、读取慢」：可能要优化存储格式（如 TFRecord）、加缓存或提升 I/O 吞吐。
  • 强调「多卡、要扩展」：才会考虑 DDP 之类的分布式策略。

【一句话记住】

> 看监控定瓶颈：CPU 高 / GPU 低 → 优化数据加载（num_workers、pin_memory、prefetch）；GPU 高 / CPU 低 → 才加算力或上 AMP。

【这道题在说什么】

你在用 Kubeflow Pipelines（KFP）的 SDK 写一条机器学习流水线，这条流水线会跑在 Google 托管的 Agent Platform Pipelines 上。流水线里有一个预处理组件，跑一次要两个小时；而你现在反复迭代的是它后面的模型训练组件，所以每改一次代码你就得把整条流水线重新提交一遍，既费时又费钱。你的诉求很明确：预处理组件只有在它的输入数据或参数真的变了才重新跑，其他时候直接跳过；并且要最省力、最省钱、最省时间。

【先搞懂几个概念】

  • 机器学习流水线（ML pipeline）：把「读数据 → 预处理 → 训练 → 评估 → 部署」这些步骤像工厂流水线一样串起来自动执行，每一步叫一个「组件」。好处是可复现、可复用——你只改某个工位，不必把别的工位重做一遍。
  • Kubeflow Pipelines（KFP）SDK：用 Python 定义流水线的工具库，你写的组件会被编译成托管服务能执行的格式。它本身不代表「会自动复用」，复用要靠缓存机制。
  • Agent Platform Pipelines（原 Vertex AI Pipelines）：Google Cloud 上的托管流水线编排服务。托管＝你只管提交，服务器、扩缩容、调度都由 Google 管，运维量小。
  • 组件级执行缓存（execution caching）：本题的核心。KFP 会给每个组件算一个「指纹」（缓存键）——把该组件的输入参数、输入数据产物的引用地址、组件代码等拼起来做哈希。下一次运行时，如果算出来的指纹和历史上某次完全一样，系统就直接跳过执行，把上次的输出产物拿过来用，这叫「缓存命中」。
  • 产物（artifact）与输出 URI：组件跑完产生的文件（比如预处理后的数据集）会存到某个地址，比如 Cloud Storage 里的一串 URI。下游组件正是通过这个地址来读取上游结果。
  • 哈希 / 缓存键（cache key）：把一组输入压成一个短字符串，输入不变则键不变，用来判断「这两个运行是不是等价，能不能复用」。

在预处理组件上加入 set_caching_options(enable_caching=True)，即为该组件开启执行缓存。工作机理是：KFP 在每次准备运行这个组件之前，会根据它的输入参数、输入 artifact 的内容或引用、组件镜像与代码等算出一个缓存键；如果历史运行里存在相同缓存键的记录，就直接复用那份输出产物，不再真正执行那两小时的预处理；一旦你改了输入数据或参数，缓存键就会变化，缓存失效，组件自动重跑。它完全以「输入/参数是否变化」为判据，精准命中约束；而且只需要在组件上加一行方法调用，工作量、成本与总执行时间都是最小的。

【其他选项为什么不行】

  • 选项 B（Experiments 追踪血缘 + 手工传 URI）：Agent Platform Experiments（实验跟踪服务）是真实存在的功能，用来记录每次运行的血缘（lineage）、指标与产物关系，方便你回溯「这个模型是哪次数据、哪次代码训出来的」。它适合做实验管理与可观测性；但它本身不会让预处理「跳过执行」。手工把上一次的产物 URI 塞进训练组件，等于把依赖硬编码进去：一旦你换了输入数据，你依然要靠人记得去改那个 URI，既不自洽也不自动。它解决的是「看得见」，不是「自动少跑」。
  • 选项 C（跨运行共享的 PVC）：Persistent Volume Claim 是 Kubernetes 里申请持久化存储的方式，让容器重启后数据还在，是真实能力，适合需要跨 Pod、跨重启共享文件的场景。但在托管的 Agent Platform Pipelines 里，不同运行之间的容器默认并不共享同一块持久卷，需要额外挂载与配置；更关键的是，PVC 只能「让数据留下来」，它没有任何逻辑去比较「本次输入与上次是否相同」，所以无法决定跳过与否，反而增加运维复杂度。
  • 选项 D（dsl.Condition + 时间窗判断）：dsl.Condition 是 KFP 里的条件分支，让流水线根据某个布尔条件走不同路径，是真实且有价值的控制流工具。但用「预处理在过去一小时内是否执行过」来判定，与「输入/参数有没有变化」毫无因果关系：你改了数据但一小时内跑过，就会被错误跳过，算出的模型是错的；你没改数据但距上次超过一小时，又会白白重跑两小时。判据本身错误，必然误判，既不省时间也不正确。

【这个考点还会怎么考】

  • 变体一：把「预处理」换成「一个很贵的评估组件」，场景仍是「只改下游、上游别重跑」→ 答案依旧是开启组件缓存，成本驱动的逻辑不变。
  • 变体二：问「某个参数（如随机种子、时间戳）不应导致缓存失效」→ 考的是如何忽略某些参数对缓存键的影响，仍属执行缓存的知识范畴。
  • 变体三：把场景改成「代码仓库里的代码变了才重新训练」→ 那就不再是组件缓存，而是事件驱动的 CI 触发器（见本批 374 题的 Cloud Build 触发器）。
  • 变体四：问「如何让不同流水线之间共享同一份缓存结果」→ 仍选执行缓存机制，而不是挂载共享盘或手工传 URI。

【一句话记住】

> 输入或参数没变就别重跑 → 给该组件开执行缓存 enable_caching=True。

核心考点：超大模型训练的显存优化与并行策略

【这道题在说什么】

你在训练一个 1750 亿参数的大语言模型，用了一块包含 32 块芯片的 TPU v5p Pod 切片。一开始你用的是标准数据并行，结果任务立刻因为显存不够（OOM，out-of-memory）崩掉。你现在要换一种训练策略，目标有两个：第一，彻底解决内存装不下的问题；第二，尽量不拖慢训练速度（最小化训练延迟）。这道题的陷阱在于：很多人第一反应是「加芯片」或「省显存」，但这两条路要么治不了根，要么会明显拖慢训练。

【先搞懂几个概念】

  • 参数（parameters）：模型里可学习的权重，175B 就是 1750 亿个。参数量越大，模型能表达的能力越强，但也越吃显存。
  • 显存与 OOM：加速器（GPU/TPU）上的内存有限，训练时要同时放四样东西——参数、梯度、优化器状态、中间激活值。任何一样放不下都会报 out-of-memory，任务直接失败。
  • 数据并行（data parallelism）：把不同批次的数据分给不同芯片，每块芯片都保存一份「完整模型副本」，各自算梯度再互相同步。它简单、通信效率高，但代价是每块芯片都必须装下整个模型——这正是本题 OOM 的根源。
  • 优化器状态（optimizer states）：优化器（如 Adam）会为每个参数额外保存动量、方差等数值，总量常常是参数量的 2～3 倍，是显存占用的最大头之一。很多人只算「参数多大」，忽略了优化器状态，才低估了显存需求。
  • 梯度检查点（gradient checkpointing）：反向传播时不保存所有中间激活，而是丢弃一部分、需要时用前向重算，用额外计算换取显存。
  • 分片（sharding）/ ZeRO / FSDP：把参数、梯度、优化器状态切开放到不同芯片上，每块只保存一部分，单芯片占用大幅下降；计算时按需从其他芯片聚合。本质是「数据并行 + 状态分片」，业界又称 ZeRO（零冗余优化器）或 FSDP（完全分片数据并行）。
  • 张量并行 / 流水线并行：把单层的计算切开、或把不同层分到不同芯片，属于模型并行；能省显存但通信复杂、实现难度高，延迟不一定更优。
  • TPU v5p Pod：Google 的高性能 TPU 集群，一个 Pod 切片由多块芯片经高速互联组成，芯片之间带宽很高，适合做分片通信。

  • 「175B 参数 + 标准数据并行立刻 OOM」→ 根因是每块芯片都要装完整模型（含庞大的优化器状态），必须减少单芯片显存占用。
  • 「最小化训练延迟」→ 方案不能大幅牺牲吞吐；参数服务器会拖慢，只开梯度检查点也会拖慢。

【其他选项为什么不行】

  • 选项 A（参数服务器 + 权重放 CPU 内存）：参数服务器是真实存在且历史上广泛使用的架构，适合推荐系统里超大稀疏 Embedding。但把权重放在主机 CPU 内存后，每次前向/反向都要把参数在 CPU 与加速器之间搬运，受 PCIe/网络带宽瓶颈严重拖累，训练明显变慢，直接违背「最小化延迟」，而且它本身也不可扩展。
  • 选项 B（梯度检查点 + 继续数据并行）：gradient checkpointing 是合法的省显存技术，适合「激活值占显存很大」的场景。但它以额外计算换显存，会增加延迟；而且对 175B 规模，仅靠重算激活通常仍然放不下庞大的参数与优化器状态，内存问题未必解决。只做它不够，且与「最小延迟」有冲突。
  • 选项 D（扩容更多芯片 + 继续数据并行）：TPU 扩容是真实能力。但标准数据并行下，每块芯片依旧持有完整模型副本，OOM 依然会发生——增加芯片数并不能降低单份副本的显存需求。属于「扩容了但没改策略」的无效解。

  • 变体二：强调「网络带宽受限、推理要极低延迟」→ 讨论张量并行/流水线并行的取舍，或混合并行。
  • 变体三：问「如何在固定芯片数下装下更大的模型」→ 参数/状态分片（ZeRO/FSDP）仍是首选。
  • 变体四：问「推理阶段的显存优化」→ 量化、KV cache 优化、批处理等，考点完全不同，不要混淆训练与推理。

【一句话记住】

> 超大模型训练 OOM 且要低延迟 → 分片参数与优化器状态（ZeRO/FSDP），别只加芯片或只开 checkpointing。

  • 「回复事实上正确、只是详略不合期望」→ 说明问题出在风格而非知识，用微调对齐风格最对症。
  • 「数千行反馈」→ 数据量足够支撑一次监督微调，不需要额外收集海量数据。

【其他选项为什么不行】

  • 选项 A（Model Garden 换模型 + A/B 测试）：Model Garden 与 A/B 测试都是真实能力，适合从现成模型里挑整体表现更好的一个。但换模型只能选一个全局较好的，无法针对「按问题类型调节详略」这种细粒度偏好做定制，很可能换了还是老问题。
  • 选项 B（改提示词列举场景）：修改提示词是最轻量的手段，适合快速试验。但要人工穷举所有场景，覆盖不全；需求一变就得改 prompt，而且无法泛化到未列出的情况，不属于可扩展方案。
  • 选项 C（关键词路由）：关键词路由是真实做法，适合极少数、意图非常明确的场景。但「detailed / fact」这类词并不一定反映用户的真实意图，规则脆弱、容易误判，且需要持续维护，可扩展性差。

【这个考点还会怎么考】

  • 变体一：改成「只需临时微调、样本很少」→ 提示工程可能就够用。
  • 变体二：改成「要让模型掌握特定事实/知识」→ RAG（检索增强生成）通常比 SFT 更合适，因为知识会更新。
  • 变体三：改成「要在多个现成模型里挑一个整体最好的」→ Model Garden + A/B 测试。
  • 变体四：改成「需要模型严格按固定格式输出」→ 提示工程加受约束解码，或 SFT。
  • 变体五：改成「有用户偏好排序数据（哪个回答更好）」→ 可考虑基于人类反馈的偏好优化方法，而非单纯的 SFT。

【一句话记住】

> 有大量用户偏好、要让模型系统性对齐某种风格 → 整理成数据集做 SFT；换模型/改提示/关键词路由都不够可扩展。

【先搞懂几个概念】

  • 持续训练（CT, continuous training）：代码或数据一变就自动重新训练模型，是 MLOps（机器学习运维）里的自动化环节，地位类似于软件工程里的 CI/CD。
  • CI/CD 与单元测试：代码提交后自动跑测试、构建、部署的实践；单元测试用于验证代码逻辑是否仍然正确，是自动化流水线的第一道关。

  • Agent Platform Pipelines（Vertex AI Pipelines）：托管流水线编排服务，用来把训练、评估、部署串成可复现的流水线。
  • 模型评估组件（model evaluation component）：在流水线里对模型计算指标并与基线比较，作为「部署前门禁」，决定新模型要不要上线。

  • Cloud Run function / Cloud Workflow：无服务器函数 / 通用工作流编排，都是托管服务，但用途与适配场景不同。

【其他选项为什么不行】

  • 选项 A（Cloud Run 函数 + Model Monitoring）：Cloud Run 函数是真实的无服务器计算，能响应提交。但它不是仓库原生的 CI 编排，触发与流程都要自己处理，等于自己再造一套 CI；更关键的是 Model Monitoring 用于「线上漂移监控」，不是部署前的性能校验，工具用错了地方。

【这道题在说什么】

你在用 Gemini Enterprise Agent Platform 给一个在线游戏社区部署生成式 AI 聊天机器人。Beta 测试期间你发现，用户能输入恶意提示词，诱导模型生成仇恨言论和暴力内容。你要在生产环境加一道护栏（guardrail）来拦截这类内容，并且开发开销要尽可能小。这道题考的是：生产环境的生成式内容安全，要靠可靠且配置即用的托管能力，而不是靠一句「请你别乱说」的软提示，也不该上成本很高的重方案。

【先搞懂几个概念】

  • 护栏（guardrail）：加在模型输入/输出侧的安全防线，用于拦截或净化有害内容，是生成式应用走向生产环境的必备组件。
  • 输入护栏 vs 输出护栏：输入护栏在恶意提示到达模型前就拦下；输出护栏在模型吐出有害内容后拦截/净化。理想方案两者都要覆盖。
  • Model Armor：Google 托管的大模型安全服务，可配置策略来检测、拦截或净化仇恨、暴力等有害内容，也能防提示注入。托管、配置即用，无需自研模型，且策略可持续维护、统一治理。
  • 系统指令（system prompt）：给模型的全局行为设定，灵活方便，但属于软约束，容易被越狱式提示绕过。
  • 监督微调（SFT）：用数据集继续训练模型，成本高、周期长，且难以覆盖不断出现的新型攻击。
  • 越狱（jailbreak）/ 恶意提示：诱导模型绕过安全限制的输入，是本题的威胁来源；攻击手法会不断演化。
  • 内容审核分类 vs 生成式安全：传统内容审核是对一段文本做「有害/无害」分类；生成式安全还要覆盖提示注入、越狱、模型输出等多个环节，需求更复杂。
  • Cloud Natural Language API：传统的自然语言理解服务，包含内容审核分类能力，可用来判断文本是否有害，但需要你在应用里自行集成，且它不是为生成式输入/输出流设计的。
  • 提示注入（prompt injection）：把恶意指令混进输入来劫持模型行为。

【其他选项为什么不行】

  • 选项 A（修改系统指令）：修改系统指令是真实且常用的手段，适合一般的行为引导。但它是软约束，容易被越狱式提示绕过，攻击者稍作伪装就能突破，不能作为可靠的生产护栏，不满足「在生产环境中拦截」的可靠性要求。
